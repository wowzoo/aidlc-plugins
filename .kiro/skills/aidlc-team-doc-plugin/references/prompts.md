## dry run — `plugin-doc-dryrun` 에게

```
<stage 파일>, <agent 파일>, <템플릿 파일> 을 끝까지 읽어라. 세 파일은 고치지 마라.
<record> 는 <시험 record 폴더의 절대 경로> 다. 먼저 그 아래 트리를 나열하고, 있는 입력만 읽어라.
stage 의 Step 1 부터 HTML 변환 Step(<HTML 변환 Step 번호>)까지 수행해 <record>/<phase>/<stage slug>/ 아래에 문서를 쓰고 HTML 로 바꿔라.
문서 정보의 intent slug 는 `dry-run`, 작성일은 오늘 날짜로 써라.
HTML 변환 Step 은 아직 설치 전이므로 stage 에 적힌 명령 대신 이렇게 실행하라:
  bun "<원본 plugin 절대 경로>/tools/<HTML 도구 파일>" "<네가 쓴 md 의 절대 경로>"
stage 파일의 명령은 고치지 마라.
그 뒤의 Step(엔진에 완료 보고, 승인 요청)은 하지 마라. aidlc 명령은 실행하지 마라.
<record> 밖에는 아무것도 쓰지 마라.

다음을 보고하라.
(a) stage 의 승인 Step 이 보여 주라는 숫자
(b) 템플릿이 애매하거나 아무 말도 하지 않아 네가 스스로 판단한 곳 전부.
    템플릿 문장을 인용하고, 무엇으로 정했는지 적어라. 없으면 "없다" 고 분명히 써라.
(c) 입력에 있었지만 문서의 어느 칸에도 넣지 못한 사실
```

## 엔지니어링 검토 — `plugin-doc-reviewer` 에게 (1회차)

```
plugin 산출물이 설치된 AI-DLC 엔진이 실제로 하지 않는 일을 주장하는 곳을 찾아라.
파일을 고치지 마라. 테스트 · 빌드 · aidlc config · sync 같은 쓰는 명령을 실행하지 마라. 읽기만 하라.

검토 대상: <SRC 절대 경로> 아래의 새 stage · 템플릿 · 바뀐 README, 그리고 <바뀐 문서 경로들>.
1차 출처 — 줄 번호는 여기서만 검증하라:
- 설치된 엔진 트리: <PROJECT>/<LEAF>/  (버전: <aidlc --version 결과>)
- 플러그인이 설치된 트리: <PROJECT>

오늘 측정한 것(기억이 아니라 측정): <5단계 스크립트 출력 요약 — VALID/CLEAN/drops/doctor/graph scope 결과>

내가 세운 인과:
<새 stage 가 어디에 붙고, 무엇을 읽고, 무엇을 쓰며, 어떤 명령을 실행하는지 한 문단>

판정하라.
a) 전달 경로: 새 stage 가 쓰는 명령 · 경로 · 산출물이 설치본에서 실제로 그렇게 동작하는가. 각 항목에 파일:줄.
b) 분기: 입력이 없을 때, 건너뛰어질 때, 재실행 · 게이트 수정 때 지시가 맞는가.
c) 문서의 주장 중 설치본과 어긋나는 문장. 원문 인용 + 반박하는 파일:줄.
내가 틀렸다고 보면 분명히 말하고, 진짜 결함이 어느 파일에 있는지 말하라.
```

## 편집장 검토 — `plugin-doc-reviewer` 에게 (2회차부터)

```
당신은 개발자용 기술 가이드를 다루는 출판사의 편집장이다. 저자에게 듣기 좋은 말을 해주는 사람이 아니라,
독자와 AI 가 이 묶음만 들고 일을 해낼 수 있는지 판정하는 사람이다. 파일을 수정하지 마라. 판정만 하라.
<검토 기록 폴더> 는 읽지 마라.

검토 범위: <새 stage · 템플릿 · agent · 바뀐 README · 그것들이 참조하는 plugin 지시문 전체의 경로 목록>
독자: 팀 문서 plugin 을 이어서 만드는 개발자와, 이 지시문을 실행하는 AI agent.
글의 성격: AI-DLC <버전> 기준 실무 문서다. 엔진 명세서가 아니다.
  담은 내용이 틀렸거나, 따라 하다 실패하거나, 실행 중에 잘못 동작하는 곳만 결격이다.
1차 출처: <PROJECT>/<LEAF>/ . 줄 번호는 여기서만 검증하라.

지난 회차 이후 반영한 것 — 각 항목은 1차 출처에서 확인했고, 바뀐 명령은 문서에서 뽑아 공백 경로 bash 로 실행해 확인했다:
<항목별 목록>

재판정 요구 — 지난 회차 지적 중 1차 출처에서 틀렸다고 확인한 것:
<지적 · 내가 본 근거 파일:줄 · "이 판단이 맞는지 1차 출처로 확인해 판정하라">

판정하라.
1. 지난 회차 지적이 항목별로 해소됐는가.
2. 범위 전체에서 남은 결함을 빠짐없이: 명령(bash · 공백 경로 · 실행 위치 · harness 바꾸기), 사실(설치본과 어긋남),
   문서 간 모순, plugin 지시문의 동작(실행 시점 · 분기 누락 · 입력 경로 · 재실행). 없으면 "없다".
3. 새로 생긴 문제. 없으면 "없다".
4. 등급 A / B / C 와 근거 한 문장.
   기준은 "이 묶음을 그대로 넘겨 독자와 AI 가 일을 해낼 수 있는가" 다.
   문체 취향, 더 나은 대안의 존재, 추가로 다듬을 여지만으로 B 에 묶어두지 마라.
   실제 동작을 잘못 이해하거나, 따라 하다 실패하거나, 실행 중에 잘못 동작할 서술이 남았을 때만 B 다.
   남은 지적이 모두 "더 자세히 쓸 수도 있다" 수준이면 A 로 판정하라.
지적할 때는 원문을 인용하고 대안을 함께 제시하라. 한국어로.
```
